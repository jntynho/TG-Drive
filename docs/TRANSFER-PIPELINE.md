# Upload pipeline — 0.5

The sender is shared by an account library and serializes document, text and delete requests. Explicit server retry seconds become a durable `sendCooldownUntil` in that account's encrypted database. Retry cannot bypass it. A one-second safety margin follows the server deadline. Successful sends slowly reduce conservative spacing; a rate-limit response increases spacing. These are implementation heuristics, not published Telegram quotas or an exemption from provider limits. Read/playback work is not intentionally stopped by the send lane.

Journal operations retain their schema-2 identities, encrypted vault bodies, parent relationships and conflict semantics. Up to 32 operations (bounded by uncompressed size) travel in one `TGDRIVE-BATCH/2` message/document. Readers accept old single-operation messages/documents and new batches. **Update all TG Drive installations to 0.5 or later before using batched uploads: older clients cannot read the new batch transport.** Existing files and legacy metadata are not rewritten or deleted by upgrading.

Uploads have a durable SYNCING_METADATA stage. Acknowledged content is not sent again when only the journal send failed. Completion callbacks and backup receipts are replayable/idempotent and flagged durably after completion. Deleting one file from a shared metadata batch first relocates surviving operations and only then removes that batch, preserving the other files' recovery information.

A single next non-vault file may be snapshotted in private staging while the current transfer runs, only when its size is known and at most 16 MiB and free-space checks pass. Its bounded snapshot is rehashed before use; the original URI remains associated with the uploaded source for later independent cleanup verification. Vault sources do not acquire a plaintext staging snapshot. Unknown/larger sources use the normal bounded part path. The snapshot is the content captured during preparation; external edits after capture do not silently alter it. Preparation failure falls back to the normal path and does not mark an upload successful.

Cache metrics no longer require a filesystem traversal whenever metadata is published. Maintenance runs at most once per 30 seconds during normal work, with an immediate low-space path and explicit storage-setting/cleanup operations. Active leases and offline copies retain their existing protection.

Synthetic integration evidence: five different small file uploads generate one metadata batch containing ten operations, rather than ten separate metadata sends. Tests cover metadata failure without content re-upload, account cooldown persistence/manual retry, recovery codecs, and shared-batch deletion. This measures message reduction in a fake transport, not a live throughput improvement. Encrypted thumbnail documents are intentionally retained; plaintext preview shortcuts would weaken vault privacy. No new runtime/network service is required.

Automatic resume uses Android WorkManager and is subject to Android scheduling/battery rules; the exact second of execution cannot be guaranteed. Telegram may still impose limits. The optional manual upload-pace setting remains respected.
